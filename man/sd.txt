NAME
    sd - the SD card: information, speed, unmounting, checks, benchmark, format

SYNOPSIS
    sd
    sd info
    sd speed [<MHz>]                      (change: console only)
    sd unmount                            (console only)
    sd check                              (console only)
    sd check fix                          (console only)
    sd test [<KB> [keep]]                 (console only)
    sd format [exfat | fat32] [plain]     (console only)

DESCRIPTION
    'sd' (or 'sd info') shows the card and volume information, the SPI clock,
    and whether the card is encrypted, with its card id. 'sd speed' shows the
    SPI clock, set and actual; 'sd speed <MHz>' sets it (1 to 75) and
    reinitializes the card; not saved.

    'sd unmount' unmounts the card before it is taken out; refused while a
    file is open. No card-detect switch is wired by default, so the board
    doesn't notice a swap: unmount, swap, and the next file command mounts
    the new card.

    'sd check' checks the card's file system (exFAT or FAT32) for damage,
    such as a power cut during a write leaves: lost clusters, files whose
    size doesn't match their clusters, clusters two files share, broken
    directory entries. It runs only on an unmounted card: run 'sd unmount'
    first. While it runs nothing else uses the card: file commands, SFTP,
    Lua fail as if there were no card, TLS roots not loaded yet can't be
    read (roots already in memory still work), the log files wait, and the
    other 'sd' commands refuse. It prints one line per problem, then
    a summary, which also goes to the log. It never writes to the card;
    'sd check fix' repairs. Ctrl-C stops it. Afterwards the card is
    left as 'sd unmount' leaves it: the next file command mounts it.
    The report can't go to a file on the card: 'sd check > file' opens the
    file first, which mounts the card, so the check refuses ('the card is
    mounted') and that line is what lands in the file. 'sd check | more'
    works.

    The report starts with 'checking exFAT, <size>, <n> clusters of <size>,
    encrypted (<n> passes)', then 'pass <i>/<n>' lines; the clusters are
    checked a window at a time, one pass over the directories per window.
    Problems start with the path when there is one ('/a/b.txt: chain
    loops'). Lines about clusters: 'lost: clusters <a>-<b> (<size>)' (in
    use, reached by no file), 'reached but free: ...' (exFAT: used by a
    file but free in the allocation bitmap), '<path>: cross-linked with an
    earlier entry', and on exFAT '<n> clusters used by more than one entry'
    when no file can be named. exFAT also has 'up-case table checksum ...'
    and 'the allocation bitmap's chain isn't contiguous ...' (FatFs won't
    mount such a card). Lines starting 'note:' aren't problems: a chain
    longer than its file, a stale free count, the volume flagged dirty or
    as having had a disk error (left by a PC or camera; also in the
    summary), FAT entry 0 not matching the media byte, an up-case table
    unlike FatFs's. A card that can't be checked at all ends with 'not
    checked: <why>' (no card, no volume, a boot sector FatFs would refuse).

    'sd check fix' checks the same way, then repairs what can be repaired
    without losing data a file still reaches: lost clusters are freed,
    chains longer than their file are cut to the file's size (the rest
    freed), a second FAT that differs from the first gets the first's
    sectors, and FSInfo's free count is set to unknown so that the next
    mount counts it again. FAT32 only for now: on exFAT it ends 'not
    repaired: exFAT repair isn't built yet'. It never touches cross-linked
    files, broken or short chains, damaged directory entries or names, the
    boot sector or the partition table: each of those means choosing whose
    data wins, which is for a PC and a backup. With cross-links on the card
    it doesn't cut chains either ('trims skipped: cross-linked files, fix
    those on a PC first'), and when part of the directory tree couldn't be
    read it frees and cuts nothing, since what that part holds would look
    lost. An empty file that still has clusters is left as it is.

    After the check it shows the plan: 'to repair:' with a line per kind
    and its count, 'left alone:' with what it skips and why, and asks for
    'yes', as 'sd format' does. Anything else ends it with 'not repaired',
    and nothing has been written. A plan with nothing to write
    ends with 'nothing to repair' instead. On 'yes' it repairs, one sector
    at a time, then checks the card again: 'repaired: <what>; <n> sectors
    written', then 'after repair: <summary>'. The plan, what was written
    and the summary go to the log ('sd: check fix: ...').

    It can stop at any sector, by Ctrl-C, a write error or a power cut,
    and the card is no worse than before: files read the same bytes, and a
    check finds the problems it found before or fewer, plus at most a note
    that the two FATs differ and lost clusters at the end of a chain being
    cut (space, not data: 'sd check fix' again frees them). A write error
    ends it with 'stopped: write error at sector <n>; the card is no worse
    than before (sd check shows what is left)'. A card that lost power
    during a write can still hold a half-written sector, which no order of
    writes prevents: check it again before use. Like 'sd check', it is
    console only, runs only on an unmounted card, and nothing else uses the
    card until it ends, the question included.

    'sd test [<KB> [keep]]' is a write and read benchmark: 4 to 65536 KB,
    default 256; everything else waits until it finishes. 'keep' leaves
    /sos-test.txt on the card.

    'sd format' erases the whole card (all partitions) and formats it with
    one partition, exFAT by default, after you type 'yes'. The card is
    ENCRYPTED (XTS-AES-128, with a new key this board keeps) unless 'plain'
    is given; a PC sees an encrypted card as unformatted. When an encrypted
    format finishes it shows the card's id and data key, ONCE: store the key
    offline, it is the only way to read the card if the board is lost or its
    configuration erased (tools/host/sdcrypt.c, or cryptsetup). It can't be
    shown again later. Old files on the card aren't erased: what was written
    unencrypted before stays readable until overwritten. SSH sessions pause
    until the format finishes.

    An encrypted card's key is stored on the card, wrapped with a key made
    from the board's root secret and the owner secret in its configuration,
    so the card unlocks at boot with nobody logged in and survives
    reflashing. Erasing the configuration ('config reset', provisioning,
    erasing over USB) locks the board's cards: that is deliberate. A card made
    by another board is refused; 'sd format' erases it for use here.
    Encryption is software AES: about 1.1 MB/s write and 1.0 MB/s read,
    against 2.0 / 1.7 MB/s unencrypted.
