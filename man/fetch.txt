NAME
    fetch - download a file over HTTPS or HTTP

SYNOPSIS
    fetch [-f] [-k] <url> [<file>]

DESCRIPTION
    Downloads <url> and saves the body exactly as received. Without <file>,
    the name is the last part of the URL's path, percent-decoded ('%20' is a
    space); a URL that ends in '/' or whose name can't be a file name on the
    card needs a <file>. That includes a name FatFs would store differently,
    such as one ending in a dot or a space: it is refused rather than
    changed, and giving <file> is the way round it. A directory as <file>
    saves the URL's name inside it.

    The body goes to <file>.part first and is renamed to <file> only once it
    is complete: the length the server announced arrived, or the last chunk,
    or the server ended TLS cleanly (on plain http: closed the connection,
    see below). A failure or Ctrl-C deletes the .part,
    so a cut download never looks finished. An existing <file> isn't replaced
    without -f; with -f it is moved aside to <file>.old until the download
    has taken its name, so a failed rename loses neither.

    Only a 2xx status saves anything. Any other status prints the status line
    and the first 256 bytes of what came with it, filtered as 'http get'
    filters text, and saves nothing.

    On the console a progress line (bytes, percent of the announced size,
    rate) is redrawn twice a second; over SSH or into a pipe only the summary
    is printed. The summary gives the size, time and rate, and the SHA-256 of
    what was written, computed as it was written, to compare with a
    published hash:

      sos> fetch https://example.org/pkg-1.2.tar.gz /apps
      -> https://cdn.example.org/pkg-1.2.tar.gz
      saved /apps/pkg-1.2.tar.gz: 183204 bytes in 2.4 s (74 KB/s)
      sha256: 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08

    Redirects (301, 302, 303, 307, 308) are followed, at most 5, each a new
    connection with its own certificate check; each hop is printed as
    '-> <url>'. A redirect from https to plain http is refused unless -k is
    given; one from http to https is always followed. A Location with a user
    name, or longer than a URL can be, is refused.

    Plain http:// URLs work too, but nothing protects them: anyone on the
    way can change the bytes or cut them short. Before the progress line,
    and for each http hop of a redirect, fetch prints

      http: not encrypted; check its hash

    so compare the SHA-256 in the summary with one published over https. A
    body with neither a length nor chunks ends when the server closes the
    connection, which is also what a cut connection looks like: the file is
    kept, and the summary adds 'size not known: check its hash'. A reset
    connection is a failure as usual, and a body with a length or chunks
    must arrive whole, as over https.

      sos> fetch http://192.168.1.20:8000/fw.bin
      http: not encrypted; check its hash
      saved /fw.bin: 5242880 bytes in 21.3 s (240 KB/s)
      sha256: 6b86b273ff34fce19d6b804eff5a3f5747ada4eaa22f1d49c01e52ddb7875b4b

    URLs must start with https:// or http:// and the path must already be
    percent-encoded. An https server's certificate must chain to one of the 2
    built-in roots (ISRG Root X1, which covers Let's Encrypt sites, and
    SSL.com's ECC root) or to one in the approved /certs/roots.pem. Many
    download hosts chain to other roots: the request then fails at the
    handshake, and fetch names the issuer it couldn't verify. Add that root
    to /certs/roots.pem and run 'tls roots approve' on the console ('man tls').

    Writes follow the same rules as 'cp': /certs and /var/log only from the
    console, the file is synced about once a second, and the card can't be
    unmounted meanwhile. One fetch runs at a time across all shells: another
    is refused with 'busy: fetch is running in another shell'. It counts as
    one of the two HTTP requests that can run at once ('man http'), https or
    plain.
