NAME
    health - self-checks of the board: the latest result of each

SYNOPSIS
    health
    health run [<name>]                 (console only)
    health full                         (console only)

DESCRIPTION
    SOS checks itself: at boot, then in the background while it runs. Each
    check reports PASS, WARN or FAIL with a short reason, or SKIP where it
    doesn't apply. 'health' shows the latest result of each check, in any
    shell: its name, status, when it was taken ('boot', '12 s ago', or 'never'
    for one that hasn't run) and the reason, then how long the boot checks
    took.

    The boot checks run before anything can make a key (in at most 100 ms):
        resets      WARN if the last reset was a fault, the watchdog or the
                    glitch detector (the text says which; see 'uptime')
        clocks      each running clock measured against its setting: WARN
                    beyond 1 %, FAIL beyond 5 %. They are measured against the
                    crystal, so this finds a PLL or divider set wrong, not a
                    crystal that drifts; the low-power oscillator's reading
                    (WARN outside 18-54 kHz) shows only a crystal about 2x off
        flash       the flash chip's JEDEC ID and size: FAIL if smaller than
                    the build expects, WARN on an unknown maker
        trng        raw bits from the random number generator's oscillator:
                    the repetition count and adaptive proportion tests of NIST
                    SP 800-90B, and the generator's own tests. FAIL refuses
                    making keys
        crypto      known answers for SHA-256, SHA-512, HMAC, AES-GCM, AES-XTS,
                    Ed25519 and X25519, and that a changed GCM ciphertext or
                    signed message is refused. FAIL refuses making keys and
                    encrypting
    The background checks read what SOS already keeps:
        glitch      every minute: WARN if the glitch detector's loop guard
                    left it off at this boot (see 'glitch')
        stack       every minute: WARN when core 0's stack peak is over 75 %
                    of its size, or core 1's (Lua) of its 32 KB; FAIL over 90 %
        heap        every minute: WARN under 64 KB free (back to PASS only
                    above 96 KB); FAIL under 16 KB (see 'mem')
        chip-temp   every minute: WARN over 70 C, FAIL over 85 C (the die's
                    temperature, see 'temp')
        supply      every minute: the lowest VSYS since the last run; on USB
                    power WARN under 4.3 V, and FAIL under 3.0 V (see 'power')

    A change of status is logged (facility kern): a FAIL at err, a WARN at
    warning, the way back to PASS at notice. A board that stays healthy logs
    one line per boot: the summary of the boot checks. A FAIL also refuses
    what depends on the check: making keys (the root secret, the owner secret,
    the SSH host key, an encrypted card, a console password's salt) or
    encrypting new data (saving the configuration). The refusal names the
    check, and the latest result counts: a check that passes again lifts it.
    Reading what is already stored is never refused. Only trng and crypto
    refuse anything.

    A fresh board whose root secret was refused this way keeps its console
    locked, saying which check failed; 'health' and 'reboot' work there.

    Lua scripts read the same results with sos.health() (see 'lua').

CONSOLE ONLY
    'health run' runs the boot and background checks now, one after the
    other, and prints each result as it comes; 'health run <name>' runs one
    check. 'health full' runs every check, including slow ones that run only
    on request (none yet). Ctrl-C stops: the check being run keeps its earlier
    result, those already done keep their new ones.
