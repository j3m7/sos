NAME
    health - self-checks of the board: the latest result of each

SYNOPSIS
    health
    health run [<name>]                 (console only)
    health full                         (console only)

DESCRIPTION
    SOS checks itself: at boot, then in the background while it runs. Each
    check reports PASS, WARN or FAIL with a short reason, or SKIP where it
    doesn't apply. 'health' shows the latest result of each check, in any
    shell: its name, status, when it was taken ('boot', '12 s ago', or 'never'
    for one that hasn't run) and the reason, then how long the boot checks
    took.

    The boot checks run before anything can make a key (in at most 100 ms):
        resets      WARN if the last reset was a fault, the watchdog, the
                    glitch detector, a brownout or a debugger (the text says
                    which; see 'uptime'), and on a boot loop: three resets in
                    a row, none asked for, each after under 3 minutes up (from
                    'uptime history')
        clocks      each running clock measured against its setting: WARN
                    beyond 1 %, FAIL beyond 5 %. They are measured against the
                    crystal, so this finds a PLL or divider set wrong, not a
                    crystal that drifts; the low-power oscillator's reading
                    (WARN outside 18-54 kHz) shows only a crystal about 2x off
        flash       the flash chip's JEDEC ID and size: FAIL if smaller than
                    the build expects, WARN on an unknown maker
        trng        raw bits from the random number generator's oscillator:
                    the repetition count and adaptive proportion tests of NIST
                    SP 800-90B, and the generator's own repetition test. FAIL
                    refuses making keys
        crypto      known answers for SHA-256, SHA-512, HMAC, AES-GCM, AES-XTS
                    and the Ed25519 public key, and that a changed GCM
                    ciphertext is refused; the text gives the time of each
                    group. FAIL refuses making keys and encrypting
    The background checks:
        crypto-ssh  30 s after boot, then daily: the known answers too slow for
                    boot, those of SSH: Ed25519 signing and verifying (and that
                    a changed message is refused), X25519. FAIL refuses as
                    crypto does
    and these read what SOS already keeps:
        glitch      every minute: WARN if the glitch detector's loop guard
                    left it off at this boot (see 'glitch')
        stack       every minute: WARN when core 0's stack peak is over 75 %
                    of its size, or core 1's (Lua) of its 32 KB; FAIL over 90 %
        heap        every minute: WARN under 64 KB free (back to PASS only
                    above 96 KB); FAIL under 16 KB (see 'mem')
        chip-temp   every minute: WARN over 70 C, FAIL over 85 C (the die's
                    temperature, see 'temp')
        supply      every minute: the lowest VSYS since the last run; on USB
                    power WARN under 4.3 V, and FAIL under 3.0 V (see 'power');
                    WARN if the brownout detector isn't on at 0.946 V
        core1       every 10 s while a Lua script runs: WARN when core 1 has
                    run no Lua for 30 s and isn't waiting for anything (a long
                    C call: Ctrl-C waits for it); FAIL when a stop was asked
                    and nothing has moved for 10 s (no scripts until reboot)
        heap-sum    every 5 minutes: the heap's totals agree (what the
                    features hold is within what is in use; in use plus free
                    is the arena); FAIL if the heap reaches the stack guard
        rtc-drift   every 10 minutes: the drift the last sync measured (see
                    'time'). WARN when the RTC is surely more than 20 ppm off
                    (with the 'time cal' value to correct it), or the board's
                    crystal more than 65 ppm; FAIL beyond 1000 ppm. SKIP until
                    two syncs, and while the uncertainty is too large to say
    and these compare what is stored with what the board uses, hourly (the
    card every 6 hours), the first a minute or so after boot. They read
    only: none writes flash, OTP or the card, or repairs anything:
        config      both configuration records: PASS when the one in use is
                    sealed and the other is empty or an older sealed one;
                    WARN when the other is damaged (no fallback if a save
                    fails), or the one in use is still plain; FAIL when no
                    record can be used though one is there (see 'config')
        rootsecret  where the root secret comes from, against the OTP flags,
                    as 'rootsecret' and 'version' say: WARN on an OTP page not
                    locked, or one flash copy damaged; FAIL with no secret
        otp         the OTP rows SOS relies on (the security flags and the boot
                    key slots, never the root secret's): WARN on a row that
                    can't be read or whose error correction doesn't match, on
                    copies that disagree, and on a public development key in a
                    release build; FAIL when secure boot is on and this
                    firmware's key is in no valid slot (see 'bootkey')
        failcount   the count of wrong console passwords: WARN when it isn't
                    zero (the text gives the count)
        hostkey     the stored SSH host key is still the one sshd serves (its
                    fingerprint in the text); FAIL if the record changed
        card        /var/log and /certs on the mounted card, and the approved
                    TLS roots against /certs/roots.pem (see 'tls'): WARN if it
                    changed since approval. SKIP while anything else has the
                    card: unmounted by hand, sd check, a format, open files

    A change of status is logged (facility kern): a FAIL at err, a WARN at
    warning, the way back to PASS at notice. A board that stays healthy logs
    one line per boot: the summary of the boot checks. A FAIL also refuses
    what depends on the check: making keys (the root secret, the owner secret,
    the SSH host key, an encrypted card, a console password's salt) or
    encrypting new data (saving the configuration). The refusal names the
    check, and the latest result counts: a check that passes again lifts it.
    Reading what is already stored is never refused. Only trng, crypto and
    crypto-ssh refuse anything: a FAIL of the others says what the board is
    doing, and the feature's own command fixes it.

    A fresh board whose root secret was refused this way keeps its console
    locked, saying which check failed; 'health' and 'reboot' work there.

    Lua scripts read the same results with sos.health() (see 'lua').

CONSOLE ONLY
    'health run' runs the boot and background checks now, one after the
    other, and prints each result as it comes; 'health run <name>' runs one
    check. 'health full' runs every check, including slow ones that run only
    on request (none yet). Ctrl-C stops: the check being run keeps its earlier
    result, those already done keep their new ones.
